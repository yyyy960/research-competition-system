# 科研竞赛管理系统 缺陷报告

- **项目**：科研竞赛管理系统（Spring Boot + MyBatis-Plus 后端 / Vue3 + Vite 前端）
- **分析基础**：193 条功能测试用例 + 131 条非功能测试用例（`功能和非功能测试用例/function-testcase-all-modules.xlsx`、`unfunction-testcase-all-modules.xlsx`）
- **分析方法**：对照每条用例的预期结果，逐一核对后端 40+ 关键文件与前端 30+ 页面/组件的实际实现
- **报告日期**：2026-08-06

---

## 一、缺陷预测总览

| 项目 | 数量 |
|------|------|
| 预测缺陷总数 | 48 项 |
| ├─ 致命（P0） | 10 项 |
| ├─ 严重（P1） | 24 项 |
| └─ 一般（P2） | 14 项 |
| 预计失败用例数 | 48 条（占总用例 14%） |
| 测试用例自身矛盾 | 5 处 |

**缺陷分布特征**（按成因聚类）：

1. **权限/所有权模型整体缺失** —— 后端绝大多数接口只有"已登录"级别的控制，没有任何资源归属校验（成果编辑/删除、通知单条操作、文件删除、用户详情读取）。
2. **前后端字段契约大面积错位** —— 约 10 处字段名不一致（submitter vs submitUserName、read vs isRead、ACTIVE vs 0/1、completionFileId vs finalMaterialFileId 等），导致按钮失效、数据静默丢失、筛选恒为空。
3. **状态机不闭环** —— "退回 → 修改 → 重新提交"流程断裂，被退回的成果永远无法再次进入审核队列；编辑不重置状态、修改日志为死代码。
4. **校验缺失** —— 文件类型、登记号格式/唯一性、时间范围、退回原因必填、新旧密码相同、分页边界等用例点名的校验均未实现。
5. **安全基线缺失** —— 无暴力破解防护、公告存储型 XSS、上传无白名单、JWT 密钥硬编码。

## 二、致命缺陷（P0，10 项）

> 以下缺陷直接导致安全类用例与核心流程用例失败。

### 缺陷 1：成果模块 update/delete 无任何所有权校验 —— 越权编辑/删除他人成果

- **证据**：
  - `backend/src/main/java/com/cms/module/competition/service/impl/CompetitionServiceImpl.java`（update 只校验状态 `pending_review`/`returned`，delete 无任何状态/所有权判断）
  - `backend/src/main/java/com/cms/module/innovation/service/impl/InnovationServiceImpl.java`
  - `backend/src/main/java/com/cms/module/copyright/service/impl/CopyrightServiceImpl.java`
  - `backend/src/main/java/com/cms/module/paper/service/impl/PaperServiceImpl.java`
  - `backend/src/main/java/com/cms/config/SecurityConfig.java`（URL 级防护仅覆盖 `/api/user/**` 和 `/api/review/**`，成果接口 PUT/DELETE 只要求"已登录"）
- **失败用例**：TC-COMP-007/008/016、TC-INNO-005/006、TC-COPY-009、TC-PAPER-005/006（STUDENT 操作他人成果应 403，实际返回 200 成功）、**TC-NF-BIZ-201**（已归档成果禁止编辑删除，实际可删）

### 缺陷 2：审核并发无锁 —— 50 并发重复审核全部成功

- **证据**：`backend/src/main/java/com/cms/module/review/service/impl/ReviewServiceImpl.java`（`approve()` 仅有 `@Transactional`，无乐观锁/行锁/synchronized，"先 select 校验状态 → 再 update"是典型 TOCTOU；四张成果表均无 version 列）
- **失败用例**：**TC-NF-REVIEW-302**（50 并发审核，期望无重复审核，实际全部通过、状态多次覆盖）、TC-REVIEW-007（重复审核拦截在并发下失效）

### 缺陷 3："退回→修改→重新提交"流程断裂 —— 状态机卡死在 returned

- **证据**：4 个成果服务的 `update()` 编辑后状态保持 `returned` 不变，系统中不存在把状态改回 `pending_review` 的"重新提交"接口；秘书/领导审核要求当前状态必须是 `pending_review`/`under_review`（`ReviewServiceImpl.java:335-340`）→ 被退回的成果永远无法被再次审核。`ModifyLogService` 全库无调用方（死代码），编辑也不写时间线。
- **失败用例**：TC-REVIEW-011、**TC-BIZ-002**（端到端退回重提）、TC-NF-BIZ-101（整改闭环）

### 缺陷 4：文件上传无类型/内容校验 —— webshell 改名即可上传

- **证据**：`backend/src/main/java/com/cms/module/file/service/impl/FileServiceImpl.java`（仅按扩展名分类入库，不校验 Content-Type/Magic Number；存储于 `/uploads/**`，在 Web 根目录下，`.jsp/.html` 可被直接访问）；文件删除（`FileController.java:71-75`）无所有权校验，任意登录用户可删任意文件
- **失败用例**：**TC-NF-FILE-202**（webshell 上传检测）、**TC-NF-FILE-203**（文件名路径遍历 —— UUID 重命名已满足）、TC-FILE-006（越权删除）

### 缺陷 5：公告存储型 XSS

- **证据**：`frontend/src/views/announcement/AnnouncementDetail.vue:48` 用 `v-html` 渲染且无 DOMPurify 清洗，后端原样存储 HTML；审核评论（comment）同样原样存储并拼进通知内容
- **失败用例**：**TC-NF-ANNC-201**（存储型 XSS 必弹窗）、TC-NF-REVIEW-202

### 缺陷 6：登录接口零暴力破解防护

- **证据**：`backend/src/main/java/com/cms/module/user/controller/AuthController.java` 无任何限流（无 RateLimiter/bucket4j/拦截器计数，pom.xml 无相关依赖）
- **失败用例**：**TC-NF-AUTH-202**（1 分钟 20 次错误密码，期望 429 或"操作过于频繁"——零实现，100% 失败）

### 缺陷 7：通知单条"标已读/删除"越权

- **证据**：`backend/src/main/java/com/cms/module/notification/service/impl/NotificationServiceImpl.java:40-47` 单条操作不校验 `userId` 归属（列表/全部操作有过滤，单条没有）
- **失败用例**：**TC-NF-NOTIF-201**（STUDENT2 操作 STUDENT1 的通知应 403，实际成功）

### 缺陷 8：Token 过期后前端不清登录态、不跳转登录页

- **证据**：后端过期 Token 返回 HTTP 403（默认 `Http403ForbiddenEntryPoint`），但 `frontend/src/utils/request.js:49-50` 的 403 分支只弹"您没有权限访问此功能"；清 Token + 跳登录的逻辑挂在 401 分支上——而后端永远不会返回 HTTP 401，该分支是死代码
- **失败用例**：**TC-AUTH-016**、**TC-NF-GLOB-201**（"403 后清除 Token 并跳转登录页"必失败）

### 缺陷 9：重复校验逻辑 4 处硬伤

- **证据**：
  - `backend/src/main/java/com/cms/module/check/DuplicateCheckController.java:38-45` competition 分支 `.and(...).or().eq(workName, ...)` 括号作用域错误，最终 SQL 为 `(名称同 OR 作品名同) OR (作品名同 AND 导师同)`——凡是竞赛名相同、不管导师是否相同的记录全被判重
  - 四类校验都不排除自己的记录（编辑时必弹"可能重复"）、不过滤 archived/returned 记录
  - 软著登记号表结构无 UNIQUE 约束（`backend/src/main/resources/schema.sql:84`），create 不拦截重复
- **失败用例**：TC-CHECK-001~006、TC-COPY-011、TC-NF-COPY-201（登记号重复应拦截，实际可重复入库）

### 缺陷 10：用户启用/禁用开关前后端契约断裂 —— 切换必 500

- **证据**：`frontend/src/views/system/user/UserManage.vue:614` 传 `status: 'ACTIVE'/'INACTIVE'` 字符串，后端 `Map<String,Integer>` 反序列化失败抛 500；前端用 `row.status === 'ACTIVE'` 判断开关态，后端返回 0/1 整数 → 开关永远显示"禁用"
- **失败用例**：TC-USER-012/013（禁用/启用用户 100% 失败）

## 五、测试用例自身的矛盾（执行前需澄清，否则必"失败"）

| # | 矛盾点 | 说明 | 建议 |
|---|--------|------|------|
| 1 | **TC-REVIEW-003 vs 需求规格** | 用例期望"秘书审核通过 → 直接 archived"，但《科研竞赛管理系统需求功能说明书》明确为两级审核（秘书通过→`under_review`，领导通过→`archived`），代码实现也是两级 | 确认以哪边为准，若以规格为准需修正用例预期结果 |
| 2 | **TC-OCR-001 vs 需求说明书** | 说明书声称"创新性地集成了 Tesseract.js 前端 OCR 引擎"（前端确实实现了真实识别），用例却期望 `/api/ocr/status` 为"存根 always unavailable"；且前端从不调用该接口 | 按说明书执行会成功、按用例执行会失败，需统一口径 |
| 3 | **TC-FILE-009 vs TC-NF-FILE-201** | 功能用例把"文件下载无需认证"当正向预期，非功能用例把同一行为标为 P0 致命安全风险 | 两条用例结论相反，需产品决策是否保留公开下载 |
| 4 | **TC-COMP-014 vs TC-CHECK-006** | `awardLevel` 一边是"非必填可空"，一边是"必填 errors 应包含" | 确认字段必填口径 |
| 5 | **TC-NF-AUTH-202** | 期望限流阈值"5-10 次"——系统没有任何限流代码，此用例无论阈值多少都失败 | 属需求未实现，建议作为新需求评审而非缺陷 |

## 七、结论

缺陷集中在三大类：

1. **权限/所有权模型整体缺失** —— 后端几乎只有"已登录"级别的控制，没有任何资源归属校验（缺陷 1、7、36、40）。
2. **前后端字段契约大面积错位** —— 约 10 处字段名不一致，导致按钮失效、数据静默丢失、筛选恒为空（缺陷 10~14、19、33、34、39）。
3. **状态机不闭环** —— 退回后无法重提，编辑不重置状态，修改日志为死代码（缺陷 3、35）。
